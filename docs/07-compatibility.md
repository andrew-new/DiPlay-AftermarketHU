# 07 — 兼容性边界与已知限制

## Android 版本之谜（未解，记录在案）

同一台车机，两个版本说法：

| 来源 | 版本 | 设备标识 |
|---|---|---|
| 车机「设置 → 关于」 | Android 8.1 Go | `YT3518C_00008_V008` / XY AUTO 3.5 |
| **5 份诊断报告（全部一致）** | **Android 6.0 API 23** | `alps evb3561sv_w_65_m0`（MTK） |

诊断报告由 App 读 `Build.VERSION` 生成，不会错。可能解释：**双系统/多分区**（5 号与 8+ 号包
跑在 6.0 分区）、或车机内有两套系统。影响与对策：

- 不影响运行：DiPlay minSdk 17/18，API 23 与 27 均兼容
- 影响适配：改包前先看报告第 3 行确认运行时 API，别信设置页
- 验证方法：重导一份报告核对头部 `Android=`

## 热点与无线

- **连接方式**：车机热点（manual hotspot）是唯一可行路径；Wi-Fi Direct 需要 Android 10+ 且
  有 RTP 丢包突发独立问题（官方 #131），不要回头试
- **iPhone 个人热点开启会阻止连接**（吉利车与本文车机都实测），连车机热点前先关 iPhone 热点
- 热点频段/信道：本机固件**无 AP 频段设置**。2.4GHz 拥堵环境下滑动码率（10-20Mbps）可能
  吃不消；无 adb 无法改信道——能做的就是 iPhone 靠近车机、避开拥堵时段
- 家用路由器实测（参考）：2.4G 环境 ping 尖峰可达 69ms / stddev 15ms——抖动普遍存在

## 硬件上限

| 项 | 数据 | 结论 |
|---|---|---|
| 解码 | MTK OMX 硬解 AVC，60% 档（614×360）解码量 -64% | 解码吞吐不是滑动卡顿主因 |
| 内存 | 2GB RAM | 100% 档（1024×536）+ 系统余量薄，内存敏感 |
| 延迟 | 投屏 RTT 物理下限 ~100ms（触摸→编码→传输→解码→显示） | 「跟手性」有架构上限，帧率正常也可能觉得卡 |

**结论**：日常使用建议 60-80% 画质档；100% 档的滑动卡顿更多是硬件余量问题而非软件 bug。

| 项 | 状态 |

| 麦克风/Siri | 未启用（`microphone:false`），未验证 |

## 改动对原功能的影响评估

每次改包按「不影响已验证功能」约束执行，验证手段：

1. **单元测试**：上游 617 项（shared + common）全过
2. **静态校验**：dex 字符串检查（新路径进包 / 旧路径 0 残留 / 关键功能字符串在位 / MFi 资产在包）
3. **diff review**：对照原始 source.zip 逐文件、排除行尾差异核对增删行数
4. **实车回归**：连接 → 声音 → 触控 → 导报告核对版本与指标
